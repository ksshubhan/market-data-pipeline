NEGATIVE CONTROL — c1_relaxed_publication, same build, same session:
WARNING: ThreadSanitizer: data race
  Read  of size 8 by thread T2: try_pop  src/spsc_ring_buffer.hpp:130
  Write of size 8 by thread T1: try_push src/spsc_ring_buffer.hpp:100
ThreadSanitizer: reported 10 warnings; process aborted, which is the
expected exit for a control.

The two lines, quoted from src/spsc_ring_buffer.hpp (192 lines):

  100:        buffer_[tail & kMask] = value;
  130:        value = buffer_[head & kMask];

Both are the payload copy — the store into the slot and the load out of
it. Neither is an index. That distinction is the result: acquire/release
exists to order the payload against the index publication, and it is the
payload TSan names when the edge is removed.

Three things this run shows that the 31 Aug artifacts could not.

The arm is the uncached one. The template signature in every frame is
SpscRingBuffer<Record, 2ul, 128ul, (SpscMemoryOrder)2, (SpscIndexCaching)0>
— five parameters. The 31 Aug report has four, and names :93 against :72,
because spsc_ring_buffer.hpp has changed since. §13 flagged the uncached
arm added in A4 as a shipped configuration that arguably ought to be
covered; the control runs it.

The tearing signature is field-by-field, and §6.5a predicted it. The ten
warnings sit at ten consecutive addresses — ...ac00, ac08, ac10, ac18,
ac20, ac28, ac30, ac38, ac40, ac48 — an eight-byte stride across ten
words, which is the 80 bytes of Record. TSan did not report "a race in the
queue". It reported the whole payload copy racing one field at a time.

The last warning is a 2-byte read against an 8-byte write, at ac48. That
is the trailing sub-word field of Record, visible as a width mismatch
because the consumer reads it narrow while the producer's store covers the
full word.

Cross-toolchain: GCC 15.2.0 with libstdc++ 15 on Ubuntu 25.10 aarch64
names the same two lines, :130 in try_pop against :100 in try_push
(evidence/tsan_gcc15_aarch64.txt, repo c3b948b). Two independently written
detectors, two operating systems, two standard libraries, one verdict —
clean on the valid arms, the same race at the same two lines on the
invalid one.

Also recorded: c1_relaxed_publication printed "no observable corruption
detected in this finite native run" while TSan reported ten races in that
same run. The program is invalid whether or not a given execution tears,
which is why the sanitiser is the evidence and the observed output is not.
